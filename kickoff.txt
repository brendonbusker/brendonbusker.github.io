You are responsible for designing, implementing, testing, configuring, and preparing for deployment a complete personal website and private content-management system.

Do not produce a generic AI-generated portfolio.

Build the entire system described below.

Where implementation decisions are not explicitly specified, make sensible production-quality choices consistent with the design philosophy and architecture in this document.

# 21. `/admin` SECURITY ARCHITECTURE

The public site must contain:

https://USERNAME.github.io/admin/

However, GitHub Pages cannot securely host the authenticated server-side application itself.

Therefore implement `/admin/` as a secure gateway into the Cloudflare-hosted CMS.

Recommended implementation:

USERNAME.github.io/admin/

shows an extremely minimal loading page:

"Opening secure editor…"

and immediately redirects with:

window.location.replace(...)

to the Cloudflare Worker admin origin.

Example:

https://personal-site-admin.USERNAME.workers.dev/

Include a normal clickable fallback link for accessibility if JavaScript is unavailable.

## Why

The CMS frontend and authentication API should live on the SAME Cloudflare origin.

This permits proper first-party:

HttpOnly
Secure
SameSite=Strict

session cookies.

Do NOT create a cross-origin authentication architecture where the GitHub Pages frontend depends on third-party cookies from workers.dev.

Do NOT put session credentials into localStorage.

The secure CMS is Worker-hosted.

The public `/admin/` route remains the human-friendly entry point.

If the site later receives a custom domain, this architecture should be easy to migrate to:

admin.example.com

# 24. PASSWORD STORAGE

Never store the plaintext password.

Use a strong server-side password verifier.

Cloudflare Workers have tight CPU limitations on the free tier, so choose the strongest password KDF that operates reliably within the current free Worker CPU budget.

Preferred order:

1. scrypt using supported Worker crypto APIs if performance is reliably within budget
2. PBKDF2-HMAC-SHA-256 using WebCrypto with a benchmarked safe iteration count
3. if neither can safely fit the free CPU budget, use a carefully documented high-entropy-password strategy with a keyed HMAC verifier and mandatory password-manager-generated password

Do NOT silently downgrade to plain SHA-256(password).

Require a very strong admin password.

Recommended policy:

at least 20 characters

Ideally use a password-manager-generated random password.

Store necessary verifier/salt/pepper values as Cloudflare Worker Secrets, not source configuration.

Create a local setup script that allows the user to enter the password interactively without putting plaintext into shell history.

Codex must never ask Brendon to paste his real password into source code or a prompt.

---

# 25. SESSION SECURITY

After successful login:

Generate a cryptographically random session token of at least 256 bits.

Store only a HASH of the token server-side in D1.

Set the raw session token only in a cookie.

Cookie requirements:

HttpOnly
Secure
SameSite=Strict
Path=/
no Domain attribute

Prefer a cookie name compatible with the `__Host-` convention.

Example:

__Host-admin_session

Session rules:

* short idle timeout, approximately 30–60 minutes
* reasonable absolute timeout, approximately 8 hours
* logout immediately invalidates session
* expired sessions rejected server-side
* session ID rotated after login
* do not reuse expired tokens
* update last activity thoughtfully without unnecessary D1 writes on every trivial request

Do not store authentication tokens in localStorage.

---

# 26. CSRF / ORIGIN PROTECTION

All mutating CMS actions must be protected.

Because admin frontend and API are same-origin:

* reject unexpected Origin headers
* use SameSite=Strict session cookies
* use CSRF tokens for state-changing operations as defense in depth
* do not enable permissive CORS
* do not use `Access-Control-Allow-Origin: *`

The admin API is NOT intended for public cross-origin consumption.

# 27. LOGIN ABUSE / BRUTE FORCE PROTECTION

This is a HARD REQUIREMENT.

The user is specifically concerned that someone may discover `/admin` and attempt huge numbers of password guesses or intentionally consume the Cloudflare free allowance.

Implement multiple layers.

## Cloudflare Rate Limiting

Use a Cloudflare Workers Rate Limiting binding.

At minimum create:

per-IP login limiter

and

global login limiter

The limiter must run BEFORE expensive password verification and BEFORE unnecessary D1 operations.

Suggested starting behavior:

Per IP:
approximately 5 attempts/minute

Global:
approximately 20–30 password-verification attempts/minute

Tune appropriately.

Return:

HTTP 429 Too Many Requests

when blocked.

Do not reveal whether the username exists.

## Turnstile

Use Cloudflare Turnstile on login.

Prefer Managed mode.

Turnstile should be configured only for the admin hostname.

Server-side validation is mandatory.

Never trust a frontend Turnstile success state without server verification.

## Failed login handling

Return the same message:

"Invalid username or password."

Never return:

"Username not found."

Do not create an account-wide lockout that lets an attacker permanently lock Brendon out.

Use throttling rather than a simplistic global account lock.

## Security logging

Record useful security events such as:

login success
login failure
rate limit
logout
expired session
rejected origin
CSRF failure

Do NOT log:

passwords
password hashes
session tokens
GitHub token
Turnstile secret
other secrets

Hash or otherwise privacy-protect IP identifiers in logs where practical.

Cap log retention.
